## Context

TrioBase 是一个多语言 Monorepo，既包含 Java/Spring/Temporal 业务服务，也包含 Python AI/数据服务、TypeScript/Vue 前端、SQL 迁移和部署配置。当前注释分布与质量不一致：部分公共契约没有语义说明，部分复杂权限和状态转换只能从实现反推；同时，简单地要求“所有代码都写注释”会诱发复述语句、过期说明和大规模无意义改动。

本治理需要同时服务开发者、代码评审者和 AI 编码工具，并兼容当前存在大量历史代码和并行变更的事实。

## Goals / Non-Goals

**Goals:**

- 用统一原则规定“何时必须写、写什么、何时不应写”，并提供各语言的规范格式。
- 对公共契约和高风险逻辑建立强制注释要求。
- 对存量代码建立可量化、分模块、可持续收敛的补齐流程。
- 对新增或修改代码执行差异化门禁，避免继续新增注释债务。
- 让规范同时进入仓库文档、AGENTS 约束、评审清单和 CI。

**Non-Goals:**

- 不要求每个字段、局部变量、getter/setter 或显而易见的控制流都有注释。
- 不以注释替代清晰命名、合理拆分、测试、API 文档或 OpenSpec。
- 不在一次机械变更中重写全仓库代码，也不修改生成代码和第三方代码。
- 不用注释记录会快速失效的实现细节、个人署名或变更历史。

## Decisions

### 1. 注释解释意图、约束和风险，不复述语法

强制内容按优先级分为两类：

1. 公共契约：模块/公共类型职责、公共接口语义、参数边界、返回与异常契约、兼容性和调用方假设。
2. 高风险实现：权限/租户/数据范围、安全过滤、事务边界、幂等键、锁与并发、Temporal 确定性、跨服务所有权、AI 工具治理、复杂状态转换、降级与补偿、非常规性能优化。

Java 使用 Javadoc，Python 使用 PEP 257 docstring，TypeScript 使用 TSDoc/JSDoc，Vue 组件在脚本中说明职责和复杂响应式副作用，SQL/迁移使用文件头与关键语句注释，YAML/脚本只解释非默认配置和运维后果。

替代方案是要求所有类型和方法达到固定注释率。该方案易被无意义模板注释满足，不能衡量理解价值，因此不采用。

### 2. 存量基线与变更门禁并行

首次扫描生成按模块分类的注释债务基线。CI 对基线中的历史缺口报告但不阻塞；对新增文件、新增公共契约，以及修改后触达的高风险逻辑执行阻塞检查。每次业务变更必须同时修复其修改范围内的注释缺口，除非存在登记过的豁免。

替代方案是一次性阻塞所有历史缺口。它会冻结正常开发，也会刺激批量生成低质量注释，因此不采用。

### 3. 自动检查负责结构，人工评审负责语义

自动化检查以下可客观判断的事项：公共契约是否存在文档块、格式是否合法、禁止标记是否带负责人和到期条件、生成目录是否排除、变更文件是否出现未解释的高风险注解或关键字。评审清单判断注释是否解释了业务原因、是否与实现一致、是否泄露敏感信息。

自动化不得仅以注释行比例作为通过条件。结构化扫描器输出稳定的规则 ID、路径和行号，并支持极少量、带原因和到期日的行级豁免。

### 4. 规范拥有单一事实源

完整规范落在 `docs/engineering/commenting-standard.md`。根 `AGENTS.md` 增加简短强制规则并链接该文档；CI、评审模板和语言配置只引用规则 ID，避免多份内容漂移。

### 5. 存量补齐按风险分波次

- Wave 1：认证授权、租户/组织数据权限、Global Action、网关脱敏、Temporal Workflow/Activity、低代码发布路径。
- Wave 2：所有公共 API、共享 DTO、事件契约、前端共享 store/composable/registry、Python 对外工具契约。
- Wave 3：其余复杂业务实现、SQL 迁移和运维配置。

每个波次以模块清单、扫描报告、人工抽查和测试结果验收，不以“注释行数”验收。

### 6. 规则分为阻断、整改和禁止三级

- `BLOCKER`：新增公共契约或高风险逻辑缺少必要说明、注释与实现矛盾、关键承诺无测试、非法豁免，CI 必须阻断。
- `ADVISORY`：可读性、格式或存量完整性问题，先报告并纳入债务，不阻断未触达代码。
- `PROHIBITED`：敏感信息、个人署名历史、无到期条件的 TODO/FIXME、注释掉的代码、批量复述式模板，CI 必须阻断新增内容。

规则级别必须在规范中明确，扫描结果不得仅输出笼统的“缺少注释”。

### 7. 注释使用中文表达业务语义并紧邻约束

仓库内部业务代码默认使用中文解释业务意图；标准协议名、代码标识符、对外 SDK 和难以准确翻译的术语保留英文。类型级注释描述跨方法不变量，局部注释放在具体决策点，避免重复的中英文双份说明。

临时说明必须包含负责人、任务标识和可验证的移除条件；永久说明只描述长期不变量。复杂决策可以引用 OpenSpec、ADR 或工单，但注释本身仍需概括原因，避免外部材料失效后代码失去上下文。

### 8. 对隐式数据语义建立专项模板

数据库字段和迁移说明业务含义、敏感等级、单位、枚举、数据假设与回滚影响；配置和 Feature Flag 说明合法范围、默认值、启停效果、生产建议、是否需要重启以及移除条件；缓存说明 Key、TTL、失效和一致性边界；并发说明锁粒度、顺序、超时和无锁不变量。

时间值必须说明时区和时间来源，金额必须说明币种、最小单位、精度与舍入，分页必须说明稳定排序和并发写入影响，事件必须说明事实语义、产生时点、顺序、重复消费与兼容策略。

### 9. 关键注释承诺必须由测试支撑

当注释声称存在默认拒绝、边界校验、降级行为、幂等保证、补偿策略、顺序保证或兼容承诺时，应存在可定位的自动化测试。扫描器可检查测试存在性和关联标识，评审者判断测试是否真正证明承诺。

并非每条说明都要求单独测试；纯职责说明、背景理由和无法通过单测表达的运维约束可由契约测试、集成测试、架构测试或人工验收支撑。

### 10. AI 只能起草注释，作者承担准确性责任

禁止仅根据名称批量生成并直接提交模板注释。AI 生成内容必须由变更作者核对业务事实、边界和测试；代码作者负责准确性，评审者负责必要性和一致性，模块负责人负责存量债务收敛。

## Risks / Trade-offs

- [自动生成低价值注释] → 禁止复述代码，以高风险场景清单和人工抽查验收。
- [注释随实现过期] → 变更必须同步更新相关注释，评审清单检查实现与注释一致性。
- [门禁误报阻塞开发] → 使用存量基线、明确排除目录和带到期日的窄范围豁免。
- [不同语言规则碎片化] → 单一规范定义共同原则，语言章节仅定义语法和惯例。
- [大范围补注释造成合并冲突] → 按模块和风险分波次，避免格式化和无关代码改动。
- [敏感信息进入注释] → 明确禁止真实密钥、个人数据、内部凭证和可利用的安全细节。
- [过度要求测试增加维护成本] → 只对可验证的关键行为承诺强制测试，背景和运维约束允许其他证据。
- [规则过多导致执行口径不一] → 使用稳定规则 ID、三级严重度、统一模板和正反例库。

## Migration Plan

1. 发布规范、AGENTS 强制条款、评审清单和规则 ID。
2. 实现只读扫描器，生成全仓库基线及 Wave 1 清单，不阻塞 CI。
3. 补齐 Wave 1 高风险路径并进行模块测试与人工抽查。
4. CI 切换为阻塞新增债务，同时继续报告存量债务。
5. 完成 Wave 2、Wave 3；每波更新基线，最终移除已清零规则的历史豁免。
6. 若门禁影响发布，可临时将对应检查降为报告模式；规范和已补注释无需回滚。
