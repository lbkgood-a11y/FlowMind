## Why

TrioBase 的权限体系已经依赖租户、主体、资源、所有者、组织、版本和审计上下文，但这些字段目前分散在各服务模型中，缺少统一的强制规则，容易出现角色无租户归属、数据权限无法编译、审计无法追责或并发更新无法检测等缺口。现在需要将“可被权限体系安全治理的模型”定义为工程契约，并纳入数据库迁移、Java 实体和 CI 门禁。

## What Changes

- 定义模型分类：租户业务事实、权限主体、授权资源、授权策略、主体关系、可变业务单据、不可变审计/事件、只读投影、平台全局配置。
- 为所有持久化模型规定基础必备字段，并为租户隔离、数据权限、乐观并发、软删除、Global Action、审计追踪等能力规定条件必备字段。
- 明确字段类型、空值、默认值、不可变性、唯一索引和外键/同租户引用要求。
- 规定平台全局数据与租户数据不得通过空 `tenant_id` 混用，使用显式作用域和值域。
- 规定权限主体、角色、资源、授权和策略必须具备可验证的租户归属。
- 规定数据权限需要稳定的所有者和组织字段，禁止依赖 JSON 临时路径作为唯一隔离依据。
- 建立 Flyway、数据库 Schema、MyBatis 实体和 ArchUnit/架构测试门禁，阻止缺少必备字段的模型进入主干。
- 给出现有表的盘点、分级迁移和兼容策略，不要求所有表机械地拥有完全相同字段。

## Capabilities

### New Capabilities

- `authorization-model-field-standard`: 定义可被 TrioBase 权限、租户、数据范围、字段规则、审计和 Global Action 安全治理的持久化模型字段契约。

### Modified Capabilities

无。

## Impact

- 所有 Java 微服务的持久化实体、MyBatis 映射、Flyway 数据库迁移与表约束。
- `common-core` 基础实体和权限/租户拦截器。
- `service-auth` 的用户、角色、授权资源、授权策略、数据策略和审计模型。
- 低代码、工作流、OpenAPI 与其他 owner 服务的业务事实、动作执行和只读投影模型。
- `common-archunit`、数据库契约测试、Checkstyle/Harness CI 门禁和模型设计文档。
